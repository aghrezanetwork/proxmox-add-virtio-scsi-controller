Adding a VirtIO SCSI Controller Alongside VMware PVSCSI

This guide describes a method tested in a real Proxmox environment: the existing VMware PVSCSI controller and the disks attached to it are preserved, and an additional VirtIO SCSI controller is introduced to QEMU so that Windows can recognize it.

Example environment: Proxmox VE 9.2, Windows 11, VMID 105. Always verify the VMID and current state in your own environment.

Before You Start: Important Notes

  • This work is for server administrators and should be performed on a test VM or one that has a backup.
  • The method below uses a custom QEMU argument; a custom controller may not enjoy the same coverage as hardware defined through the normal Proxmox UI in all management operations, migration, or troubleshooting.
  • Back up the VM configuration. This backup only keeps the configuration file, not the data on the disks.
  • If the VM already has an args: line in its configuration, do not blindly replace it — check the existing value first. The sample command may overwrite a previous args value.
  • In this scenario the second controller is added without any disks. Attaching disks to it is a separate step.
Warning: shut the VM down completely before running the final command. If the VM is important or production, test the method on a test VM first, and test Backup/Restore and Migration according to your organization's requirements.

Step 1 — Open the Shell in Proxmox

  1. Log in to the Proxmox web panel; the address is usually https://server-IP:8006.
  2. Select the target Node from the left-hand column.
  3. Open Shell. Run all commands from this guide in the Proxmox host shell, not inside the Windows guest.

Step 2 — Find the Virtual Machine ID

qm list

What it does: lists the virtual machines with their ID (VMID), name, and status.

In this guide the example ID is 105. If your VM has a different ID, replace it in the following commands.

Step 3 — Review the Current VM Configuration

qm config 105

What it does: shows the configuration of VM 105. In the example environment, the key entries were:

SettingMeaning
scsihw: pvscsiThe current SCSI controller model is VMware PVSCSI.
scsi0, scsi1, scsi2Three existing disks attached to the current SCSI controller.
ide2: local:iso/virtio-win-....isoThe VirtIO drivers ISO is attached to the VM; the path/name may differ in each environment.
machine: pc-q35-...The machine type is Q35.

If the current controller is PVSCSI, do not change the scsihw: pvscsi line; the goal is to keep it and add a second controller.

Step 4 — Back Up the Configuration File

cp /etc/pve/qemu-server/105.conf /root/105.conf.backup

Meaning of each part:

  • cp: copies the file.
  • /etc/pve/qemu-server/105.conf: the main configuration file of VM 105.
  • /root/105.conf.backup: the path where the backup copy is stored.

This command only copies the VM configuration; it does not back up the contents of the virtual disks.

To confirm the file was created:

ls -l /root/105.conf.backup

The ls -l command shows the file's existence, size, and modification time.

Step 5 — (Optional) Inspect the QEMU Command

qm showcmd 105 --pretty

What it does: displays the command Proxmox builds to run the VM under QEMU. The --pretty option makes the output more readable. This command does not start the VM or change the configuration by itself.

In the sample output, the existing controller was built with a line similar to:

-device 'pvscsi,id=scsihw0,bus=pci.0,addr=0x5'

and the disks were attached to this controller's bus. This step is useful for understanding the current state, but is not mandatory for every installation.

Step 6 — Shut Down the VM

From the Proxmox UI, shut the target VM down normally and make sure its status is stopped. Avoid force-stopping the VM unless absolutely necessary.

To check the status you can use:

qm status 105

This command shows the VM's status; the VM must be stopped before changing its configuration.

Step 7 — Add the Second (VirtIO SCSI) Controller

In the example environment, the following command was accepted and Proxmox reported that the VM configuration had been updated:

qm set 105 --args '-device virtio-scsi-pci,id=virtioscsi1,bus=pci.0'

Meaning of each part:

PartPurpose
qm set 105Modifies the configuration of VM 105.
--argsRegisters extra arguments for QEMU.
-device virtio-scsi-pciRequests creation of a virtual VirtIO SCSI controller.
id=virtioscsi1A unique internal identifier for this device in QEMU.
bus=pci.0Attaches the controller to the VM's PCI bus.
Important technical note: this command adds a custom QEMU argument to the configuration; do not treat it as the official "add a second controller" feature of the Proxmox UI. If a previous args value exists, keep it and merge it with the new argument — the command above may overwrite the previous value. Also note that a custom controller may need separate checks for migration, backup/restore, and compatibility with future versions.

Step 8 — Verify the Configuration Was Saved

qm config 105

In the output, check that a line similar to the following exists:

args: -device virtio-scsi-pci,id=virtioscsi1,bus=pci.0

This only confirms that the argument was recorded in the configuration; by itself it does not prove the controller will be created without errors when the VM runs.

Step 9 — Start the VM and Check Windows

  1. Start the virtual machine from the Proxmox UI.
  2. If the VM fails to start, do not retry repeatedly; inspect the error message and review the configuration before making further changes.
  3. Inside Windows 11, press Win + X and open Device Manager.
  4. Check the Storage controllers and Other devices sections. The device name may differ slightly depending on the QEMU version and driver.
  5. If the controller appears without a driver, use the VirtIO drivers ISO attached to the VM. Pick the driver matching your Windows version and guest architecture; avoid picking an INF file at random.
  6. After installation, check the device status in Device Manager and restart Windows if needed.

Installing the driver alone does not create the virtual controller — QEMU must present the device to the VM. Conversely, having the argument in the configuration does not guarantee Windows will recognize the device without errors.

Troubleshooting and Rollback

If the VM does not start

  • Save the full Proxmox error message.
  • Confirm the VM was stopped and that the args value does not conflict with previous arguments.
  • Do not replace the configuration file with the backup without checking it first; review the differences between the current file and the backup.

Compare the configuration with the backup

diff -u /root/105.conf.backup /etc/pve/qemu-server/105.conf

This command only shows the differences between the two files and changes nothing.

If you need to remove the custom setting

First make sure the VM is stopped and that the current args value contains only the intended argument. If args holds other settings too, deleting it entirely may remove those as well; in that case edit only the controller-related argument carefully.

If the args value is exactly the sample line and has no other settings, the custom setting can be removed with:

qm set 105 --delete args

This command removes the entire args option from the VM configuration, so only use it when you are sure nothing else is stored there. Then verify the configuration with qm config 105.

Final Checklist

  • ☐ The correct VMID was selected.
  • ☐ The configuration file was backed up.
  • ☐ The VM was stopped before the change.
  • ☐ The existing PVSCSI controller and its disks were not modified.
  • ☐ The VirtIO SCSI argument was recorded in the configuration.
  • ☐ The VM started without errors.
  • ☐ The controller was checked in Device Manager and the proper driver is installed.
  • ☐ The impact of the custom method on backup/restore and migration was tested in the target environment.
Reminder for colleagues: perform this on a test VM first. The VMID, ISO path, and Proxmox version may differ in your server. A successful result in one environment does not guarantee success everywhere.
